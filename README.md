# AR Character MVP

Прототип мобильного AR-приложения: анимированный 3D-персонаж распознаёт
поверхность в реальной комнате, встаёт на неё и реагирует на движения
телефона — бежит к краю экрана, ложится при наклоне камеры вниз, взлетает
при наклоне вверх и падает обратно, — с окклюзией по реальной геометрии
и подсветкой, подстроенной под освещение комнаты.

## Технологии

| | |
|---|---|
| Движок | Unity 6000.3.6f1 |
| Рендер | Universal Render Pipeline 17.3 |
| AR | AR Foundation 6.6.2 + ARCore XR Plugin 6.6.2 |
| Ввод | Input System 1.18 |
| Модель и анимации | Mixamo (Humanoid rig) |
| Целевая платформа | Android (ARCore, минимум API 25) |

## Архитектура

Код разделён на четыре сборки (`.asmdef`) с однонаправленными зависимостями:

```
ARCharacter.Core       — чистый C#, без единой ссылки на Unity API
ARCharacter.Runtime    — MonoBehaviour-компоненты, использует Core
ARCharacter.AR         — AR Foundation, использует Core + Runtime
ARCharacter.Editor     — сборщики сцен и ассетов, использует все три
```

Изоляция физическая, а не по соглашению: `Core` не может ссылаться на Unity
Engine-типы, `Runtime` не может ссылаться на AR Foundation — это гарантируется
компилятором, а не документацией.

### Ключевая абстракция: `IEnvironment`

Вся логика поведения персонажа не знает о существовании AR. Единственное,
что ей нужно от внешнего мира — поза камеры и поверхность:

```csharp
public interface IEnvironment
{
    Pose CameraPose { get; }
    Matrix4x4 ProjectionMatrix { get; }
    EnvironmentTracking Tracking { get; }
    bool TryGetSurface(out SurfacePlane surface);
}
```

Две реализации:

- **`MockEnvironment`** (Runtime) — квад в сцене `Sandbox.unity` и свободная
  камера, управляемая мышью. Позволяет отлаживать всю механику персонажа
  без телефона и без пересборки APK.
- **`ARFoundationEnvironment`** (AR) — та же логика поверх реального AR:
  плоскость перечитывается на каждый запрос, а не кешируется, так как
  ARCore уточняет её позу и границу по мере сканирования.

Персонаж, вся его перцепция, аниматор и взгляд на камеру собираются одним
общим кодом (`CharacterAssembly`) для обеих сцен — отличается только
источник `IEnvironment`, который в него подставляется.

## Перцепция

`PerceptionProbe` переводит положение персонажа в системе координат экрана
(вьюпорт 0..1) и фильтрует сигнал фильтром **One Euro**: в отличие от
фиксированного экспоненциального сглаживания, частота среза здесь зависит
от скорости изменения сигнала — дрожание камеры гасится сильно, а осознанное
движение проходит почти без задержки.

Точка замера считается **от опоры персонажа**, а не от его текущей мировой
позиции — важная деталь: если мерить от фактической (например, поднятой при
парении) позиции, получается замкнутая петля обратной связи между высотой
и её же измерением, которая на определённых значениях идёт вразнос.

## Поведение персонажа

Две независимые оси, а не одна общая машина состояний:

- **Локомоция** (`LocomotionResolver`) — горизонталь вьюпорта определяет,
  бежит ли персонаж к центру экрана. Пороги старта и остановки разнесены
  (гистерезис), иначе персонаж на границе дрожал бы между бегом и покоем.
- **Поза** (`PostureResolver` + `PostureStateMachine`) — вертикаль вьюпорта
  определяет позу через три перекрывающиеся полосы (Levitating / Standing /
  Flat); перекрытие полос — это и есть гистерезис, выраженный данными,
  а не веткой кода.

Состояния позы: `Standing → Flattening → Flat → StandingUp → Standing`,
а также `Levitating` и `Falling`. Падение и вставание — одноразовые клипы,
переход блокируется на время их проигрывания; единственное исключение —
вставание можно прервать подъёмом камеры (персонажа «подхватывают» на
середине). Отпущенный из парения персонаж не встаёт мягко на ноги — он
падает под настоящей гравитацией (ускоряющееся падение, а не сглаживание
к нулю) и только по достижении земли сбивается с ног той же анимацией,
что и от наклона камеры.

Во время парения персонаж держится на фиксированном расстоянии и
направлении относительно камеры — смещение пересчитывается заново каждый
кадр из текущей позы камеры, а не из накопленных дельт, поэтому реагирует
и на перемещение телефона, и на его поворот одинаково.

## Анимация

`Animator Controller` и префаб персонажа собираются кодом
(`CharacterAnimatorBuilder`), а не редактируются вручную: блендтри
локомоции (Idle ↔ Running), одноразовые состояния падения и вставания
(Mecanim сам держит последний кадр — отдельная поза лежания не нужна),
зацикленное состояние парения и три случайные вариации простоя,
запускаемые после 5–10 секунд бездействия.

Взгляд на камеру — встроенный Humanoid IK Unity (`SetLookAtWeight`),
с небольшим довторотом тела, чтобы не было эффекта «совиной головы»;
отключается на позах падения/вставания.

## AR-специфика

- **Размещение** (`ARPlacementController`) — двумя равноправными способами:
  автоматически на первой достаточно большой плоскости или вручную (сканирование
  и размещение по кнопке, с прицелом в центре экрана). Любое повторное
  размещение переставляет персонажа на новое место без потери контекста.
- **Окклюзия** (`DepthOcclusionSetup`) — включается только если устройство
  поддерживает Depth API, с явным логированием поддержки временного
  сглаживания для диагностики на конкретном устройстве.
- **Свет** (`LightEstimationSetup`) — направленный свет и ambient-освещение
  сцены подстраиваются под реальную комнату по данным ARCore.
- **AR Background Rendering Feature** — подключается к Renderer Data URP
  отдельным редакторским инструментом (`URPARBackgroundSetup`): без неё
  URP не выводит видео с камеры на экран, даже если сам `ARCameraBackground`
  настроен верно, — известная особенность связки AR Foundation + URP.
- **Тень-контактник** — отдельный шейдер (`ShadowCatcher.shader`),
  делающий плоскость невидимой везде, кроме области реальной тени от
  направленного света, чтобы персонаж не выглядел наклейкой поверх видео.

## Инструменты редактора

Сцены (`Sandbox.unity`, `AR.unity`) и Animator Controller не редактируются
вручную — они полностью пересобираются кодом через пункты меню `ARCharacter/…`.
Это осознанное решение: конфигурация воспроизводима и не зависит от
человеческой памяти о расстановке объектов в сцене.

## Тесты

EditMode-тесты покрывают чистую логику Core-слоя: проекцию камеры,
гистерезис полос позы, блокировку/прерывание переходов машины состояний,
пороги локомоции.

## Известные ограничения

- Качество и сама доступность Depth API (окклюзия, свет) зависят от
  конкретного устройства — на слабом железе возможны шум и заметное
  снижение частоты кадров при высоких настройках качества глубины.
- Окклюзия по глубине у самой поверхности, на которой стоит персонаж,
  подвержена шуму оценки глубины (известное отраслевое ограничение
  depth-based occlusion) — компенсируется небольшим постоянным зазором
  над поверхностью.
- Тень-контактник зависит от качества оценки направления света конкретным
  устройством и не гарантированно виден на всех телефонах.
